01GNC / AUTONOMY

Separation of tasks: estimate, decision, control

The central design choice is to separate the physical state, the onboard estimate, and the supervisory decision. Each has a different role and access to different information. This separation helps prevent incorrect sensor readings from directly corrupting the behavior of the entire system. Sense & estimate

Sense & estimate
Determining the satellite’s position and attitude requires information from sensors. Gyroscope and attitude-sensor measurements are processed by a multiplicative extended Kalman filter (MEKF). Each sensor provides measurements at its own frequency, while a fixed-lag replay approach allows delayed observations to be incorporated at their actual measurement time.
Guide & command
A satellite has a mission to accomplish. The guidance layer produces attitude and angular-rate references for each mission task, while the mission manager organizes priorities and transitions within the mission. The control layer then provides the actual commands to the plant. For example, in the ground-pass scenario, the learned policy generates four reaction-wheel motor commands based on tracking errors and estimated wheel authority.
Detect & supervise
This layer detects possible faults, evaluates them, and determines how the system should respond. Fault-detection logic estimates the available wheel authority from telemetry, while the supervisory logic can change operating modes or override the current target. The RL agent operates at the lowest level, controlling the reaction-wheel motors. All higher-level abstractions are implemented independently. The agent has no access to ground-truth information about wheel degradation or failures and must operate using the information provided through the observation.

Reaction wheels have a major physical limitation: momentum saturation. A reaction wheel can store only a limited amount of angular momentum before reaching its maximum rotational speed. Over time, external disturbances and the satellite’s operational tasks can cause the wheels to spin progressively faster as they compensate for accumulated angular momentum. Eventually, a wheel may reach its maximum RPM and lose the ability to provide additional control torque in the required direction. To prevent this, the spacecraft can perform momentum dumping, or desaturation, by applying an external torque while the reaction wheels are slowed back toward their normal operating range. In low Earth orbit, magnetorquers can interact with the Earth’s magnetic field to generate this external torque, allowing accumulated angular momentum to be transferred away from the reaction wheels.

02ML / RL

A small policy with a specific task

The agent is trained using the Proximal Policy Optimization (PPO) algorithm. The approximator is a small two-layer neural network with tanh activation functions. Regardless of the current system state, the agent produces commands for all four reaction wheels. The network parameters are trained to produce appropriate torque commands from the observation vector. However, the agent is responsible only for motor control. Mission guidance, supervision, fault detection, and state estimation are implemented as separate layers.

25 inputs→128 × 128 activation→4 commands

The observation contains attitude error and rate error vectors, four measured wheel speeds, four previous actions, four estimated wheel authority values, an estimator confidence value, and six supervisory mode values. The actor has 19460 parameters, making it relatively small and therefore an interesting candidate for optimization for embedded deployment. The critic is implemented separately and is not used during inference.

How the learning problem evolved

The project starts with corrections to a conventional proportional–derivative (PD) controller, then moves to direct body-torque commands, and finally to direct reaction-wheel motor commands. Each stage gives more control responsibility to the learned policy. The agent initially operates on top of a PD controller, but as the project progresses, direct control is introduced. I also deliberately use imitation of the PD controller as a training tool to provide the agent with useful initial behavior.

03SOFTWARE / EMBEDDED

Make timing and interfaces explicit

Alongside the main control work, it is important to understand what transferring this small network to a resource-constrained onboard computer would involve and how the implementation could be adapted to limited computational resources. In my experiments, I export the actor, quantize it, and run inference using a separate implementation in Rust. I deployed this implementation on a host computer as a first step toward a possible embedded implementation. This allowed me to verify the process, explore tradeoffs, understand the limitations, and identify potential problems. There are two main questions, and it is useful to evaluate them separately: (1) compare the Rust and NumPy implementations using the same observations to identify numerical differences, and (2) let the FP32 and Rust controllers run independently in closed loop from matched initial conditions. The second comparison shows how small differences in the generated actions develop over time through feedback.

During these experiments, I tried several quantization approaches but eventually focused on two formats. W8A32 stores weights as 8-bit integers and uses floating point arithmetic after reconstructing them. W8A8HI also quantizes the inputs to the later linear layers and uses integer accumulation for those layers. Its first layer keeps floating-point inputs and accumulation, while nonlinearities and output transformations also remain in floating point. From the actor–critic architecture, only the actor is required for inference. For the current actor implementation, the calculated serialized size decreases from 77896 bytes to 21344 bytes with W8A8HI, a reduction of about 72.6%. Storage reduction and inference speed are separate questions. Here, the reduction in storage size is particularly relevant for an onboard computer with limited resources.

In terms of computational cost, the dense layers require 19200 multiply–accumulate operations per inference, or 0.384 million MACs/s at 20 Hz. Bias additions, tanh, and the rest of the ADCS require additional computation. The Rust closed-loop implementation running on a host machine shows a 99th-percentile inference time of around 120 microseconds. Even a hypothetical 100 MHz processor would provide about 260 cycles per MAC, while at 10 MHz the full 50 ms budget would still correspond to roughly 26 cycles per MAC. These experiments suggest that CPU-only inference is a promising option, but measurements on a specific embedded device are still required.

04VALIDATION / INFERENCE

Demonstration of agent capabilities

I use a common experimental setup with varying conditions to demonstrate how the controller behaves as the task becomes increasingly difficult for the RL agent. Each milestone focuses on a different topic and increases the sophistication of the system, gradually moving from a simplified environment toward a more realistic ADCS simulation.

The latest completed milestone is B3, and I am still investigating several suspicious behaviors that prevent the agent from learning a better policy in B4. Another planned step is an initial open-loop interface harness for Basilisk. Numerical execution and independent closed-loop validation still need to be completed.

This is a learning and simulation project. The main result is a working chain of models, controllers, and experiments, together with enough explanation to understand how the system behaves and to continue developing it.

Scope: simulation research. Hardware transfer and flight qualification have not been demonstrated.

↳PROJECT HISTORY

Each milestone changes the problem.

  1. Foundation

    Learning with a conventional controller

    Rigid-body attitude dynamics, a PD reference controller, residual actions, and imitation learning establish a starting point.

  2. A1

    Delivered telemetry

    Gyroscope and wheel-speed samples acquire delivery timing. Attitude-error inputs still use simulator truth at this stage.

  3. A2

    Orbital context

    Orbit and sensor models add star, magnetic-field, Sun, and GNSS measurements. Generating them precedes using them for policy state estimation.

  4. A3

    Knowing the attitude

    The MEKF estimates attitude and gyro bias. Acquisition behavior becomes part of the control problem; initial delay compensation is still approximate.

  5. B1

    Closing the model gaps

    Fixed-lag measurement replay and actuator nonidealities replace earlier approximations.

  6. B2

    Fault-aware operation

    Telemetry-derived wheel authority and supervisory decisions replace privileged knowledge of injected faults.

  7. B3

    Ground-pass tracking

    Persistent mission phases, continuous references, windowed authority estimation, and magnetic momentum management connect control to a mission.

  8. C1 · ongoing

    Independent verification

    Explicit flight-style interfaces and an initial open-loop Basilisk harness establish the next validation boundary. Numerical validation remains pending.
